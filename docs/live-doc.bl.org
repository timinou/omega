#+title: Live editing of real files (omega.live-doc)

* Ownership

=live-doc.bundle.bl= is the one way the ecosystem edits a real =.bl.org= file
live. It imports through =:source/imports= like =editor.bundle.bl= and adopts no
Omega world, task or grant: a host opens its own store.

| Namespace | Owns |
|-----------+------|
| =omega.live-doc.store= | One watched shared buffer per real file (=buffer.model=): reads, waits, the guarded =update!= writer, line-range blocks |
| =omega.live-doc.blocks= | Pure line-range edits: locate a block by its exact text, replace, remove, insert |
| =omega.live-doc.host= | HTTP routes under =/_live/= (wait, block read/write, insert, client assets), owner check, same-origin writes |
| =omega.live-doc.assets= | The in-place editor (=client.js=, =client.css=), generated by =scripts/live-doc-assets.py= |

The file stays the source of truth. =buffer.model= publishes every accepted
change to disk synchronously, and its watcher adopts external writes (Emacs,
an agent shell, git) for every file someone is waiting on: it compares stat
data each =:watch-ms= (200 ms by default) and re-reads files modified within
the last two seconds, since mtimes have one-second resolution. No inotify
binary is needed. An external write that overlaps unpublished drafts is
refused as before and reported to waiters as =[:buffer/conflict path why]=.

* Host contract

1. Open a store: =(store/open!)= for an in-memory world, =(store/open! {:env e
   :server s})= inside an Omega host.
2. Mark rendered blocks with =data-src="from:to"= (source lines, end exclusive)
   and put =(host/page-config …)= in a =data-live-doc= attribute.
3. Chain =(host/handler store {:file path :editor? (host/owner-editor owner)})=
   in front of the page's routes; it answers only under its prefix.
4. Load =_live/client.js= and =_live/client.css=. Re-render on
   =live-doc:changed=, and defer it while =window.liveDoc.holding()= — checked
   again just before swapping the new body in.
5. Route the host's other writers through =store/update!= (transform returns
   ={:text :value}= or ={:error}=) so every write shares one revision stream.

Without an owner configured nobody edits; waiting and reading stay open.

* Editing model

The page stays the document's own rendering. The owner presses =E= (or the
host's Edit control) and clicks or taps a block: it opens in place as its
exact Org source, in the block's computed typography; non-prose blocks open as
monospaced source cards. It saves after 650 ms of quiet, on =Mod-S=, and when
closing (=Esc=, =Mod-Enter=, Done, a click elsewhere), then the page
re-renders. =↑=/=↓= at the first/last line walk to neighbouring blocks.

An edit names the lines it read and the exact text it started from. The store
locates that text again (nearest identical occurrence if lines moved) and
refuses when it changed, returning the current text; the client offers *Use
theirs* or *Keep mine* and never overwrites silently. Unsaved text survives a
reload in browser storage until confirmed.

* In place: edit the rendering itself

=omega.live-doc.inplace= is the editor most owners use. It is Beam Lisp,
compiled to ES modules together with the consumer's PLUG, which hands it the
very functions the server drew the page with:

| key        | value                                      |
|------------+--------------------------------------------|
| :read      | =(fn [text] {:nodes [{:line :to …}]})=     |
| :prepare   | =(fn [doc] _)= page-wide render context    |
| :render    | =(fn [node] hiccup)= one node              |
| :reparse   | =(fn [src line] node)= one node, alone     |
| :escape    | =(fn [src from to text] text)= optional    |
| :settings  | =(fn [node catalogue] [field …])=          |
| :set       | =(fn [lines node key value] {:from :before :text})= |
| :refreshed | the DOM event the host fires after a redraw |

In edit mode a click on any text makes that passage editable where it stands,
in its own typography; no source is shown. =omega.projection= aligns the
node's rendered text runs with its source bytes, splices what was typed into
exactly those bytes (markup around it untouched) and VERIFIES the edit by
drawing the reparsed node again: the edited run must read the new text,
mirrors of it (a title repeated in a label) must change alike, nothing else
may move. A refused edit is reported and nothing is written. So any renderer,
including ones nobody annotated, is edited exactly or not at all.

A gutter beside the hovered block offers =+= (insert any block of the
catalogue the host serves at =GET <prefix>/catalogue=, below) and =⋮⋮= (move
up / down, duplicate, delete with undo, settings, edit source). Settings is a
form generated from the block's parameters: enum chips, toggles, numbers,
text with suggestions. Passages it cannot map (computed text) fall through to
the source editor. Saves go through the same routes (=POST block= with the
text it replaces, =POST insert=); after a structural edit the long-poll sees
the new revision and the host redraws; the engine rereads the source on
=:refreshed=, so its line ranges and the page always describe the same text.

The host names the compiled module in =page-config= (=:inplace=, relative to
the routes); the client imports it for editors only. An open passage holds
page refreshes through =window.liveDoc.hold(predicate)=.

* Consumers

- =enchanted-skills/bl-org-dossier/kit=: every served dossier, through the
  kit's =dossier.live= (one store per VM, any number of files), which project
  hosts with their own pages call too (e.g. the Co Company map, report and
  application hosts). Its =env.bl=
  adds =~/projects/omega/src= to =:paths=, because the released =bl= that runs
  the dossier services (v2026.9–v2026.11) predates =:source/imports=. Switch it
  to the pinned bundle once a release ships source imports.
- SDKs with source imports import =live-doc.bundle.bl= by hash.
- A consumer may not import both =editor.bundle.bl= and =live-doc.bundle.bl=
  today: both list =buffer.merge=. Split it into its own bundle when one
  application needs both.
