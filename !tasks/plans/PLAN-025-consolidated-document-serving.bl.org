* Why this belongs in Omega
The literate file holds explanation, executable cells, stored results, evidence
and human decisions. Omega supplies places, navigation, editable buffers, task
references and an attention inbox. A dossier is a presentation of that same
file, rather than a separate copy of the work.

The useful loop is: open a project, understand the proposal, inspect evidence,
answer a specific question, continue the linked task, and review its changes.
The file remains usable in ordinary editors and version control. Task execution
and history retain their existing owners; they are not all forced into the file.

On 2026-11-02, the Work audit found 18 generic dossier VMs using approximately
520 MiB RSS and 1518 MiB swap in total. Related document surfaces also use custom
servers and static sites. Work already provides named services and a searchable
ports page. Reuse that infrastructure for routing and migration; Omega needs
document discovery and interactions, not another ports dashboard.

* Addresses and access
** Project addresses
=project:<place-id>/<relative-path>= opens a file in an attached place. For
example, =project:beam-lisp/research/build-unification/UNIFICATION.bl.org=.
The place supplies directory context and existing project configuration.
Opening its root shows the ordinary place and file navigation, with dossiers
discoverable by title, status, recent changes and unanswered questions.

The current workspace already has =place:=, =folder:= and =work:= providers.
=project:= is the requested public entry vocabulary, implemented in the prototype
as an adapter over the same place resolver and file identity. Do not create a second
mount table or copies of files to support it. Existing addresses keep working.

Project IDs are scoped to the authenticated account/world. Opening or attaching
a place never publishes it to other accounts. Resolve paths against the actual
attached root, including symlinks; reject escapes outside that root.

** Full file links
Accept a full host path or =file:///absolute/path/document.bl.org= in Omega's
Open action, and generate an authenticated HTTPS link for desktop and Pocket.
The server resolves the host path; a phone's local filesystem is not involved.
For example, opening the full path of =UNIFICATION.bl.org= must work without
first attaching the Beam Lisp checkout as a place.

A full file open admits exactly that document into the user's account context.
It does not attach its parent directory, grant a general filesystem browser, or
make neighboring files downloadable. A relative link opens another document
through an independently checked resolution; project attachment remains an
explicit, separate action. Discovering a file already in an attached place
reuses its existing identity and buffer.

Use the existing authenticated host/account identity and OS access boundaries.
The account association is server-owned, not supplied by a path, URL parameter
or client header. A guessed, forwarded or copied link does not transfer access,
even when the underlying file happens to be world-readable. An unauthenticated
viewer signs in; a different account is refused. Do not disclose document
titles, snippets, source, answers or evidence through unauthorized requests.

Apply the same authorization to rendered reads, raw source, revisions,
subscriptions, edits, answers, assets and linked task actions. Keep the existing
trusted identity proxy boundary; do not expose a bypass listener that accepts
client-supplied identity headers. Detaching/revoking access invalidates further
reads, writes and observation. Access must be rechecked if the resolved file
or its permissions change.

** Document identity and links
Both entry forms resolve to one account-scoped document identity, current
source revision and existing buffer owner. Read/Edit switches retain drafts,
selection and return position. Different users never share private caches,
drafts, indexes or task context merely because their paths look alike.

Copy link produces a stable authenticated document URL, optionally anchored
to a block ID. Port numbers and the current rendering mode are routing/view
details. A rename handled by Omega preserves document identity; an external
move that cannot be resolved offers recovery instead of silently selecting
another file. Historical task references retain their captured revision.

* Consolidated serving
One account host serves many admitted documents. It owns authentication,
document resolution, subscriptions and bounded render caches. A document gets
a lightweight owner/buffer and on-demand projections, not a new HTTP server
and cold BEAM for every file. Different account trust boundaries remain intact.

The request flow is: authenticate, resolve =project:= or full file address,
authorize the actual document, obtain its current buffer revision, then render
or perform a named action through the owner. Source, dossier reading, feedback
and task links all use that resolution. Opening a document never executes its
code. Explicit evaluation uses the existing project/world execution facilities
and names its target context; serving many documents does not merge their
namespaces or running applications.

Extract/reuse the dossier parser and presentation functions as an Omega bl-ed
package. Keep shared Org cell/result partitioning in =bl.doc.spans=. Domain
rendering and commands belong to the package; file IO, authentication and
accepted mutations belong to host owners. Preserve real package use/unuse and
the existing desktop/Pocket frame. Do not introduce another editor loop.

Cache projections by account/world, document identity, source revision,
renderer generation and referenced evidence revisions. A film's =run.json=,
=film.json=, failure or manifest can change without the Org source changing;
that must refresh its presentation. Bound cache entries and active observers,
coalesce rendering of the same revision, and release inactive subscriptions.

Referenced images, movies and evidence files use explicit authorized asset
resolution. Admit only required resources, never a generic directory listing.
An exact-file open does not grant access to unrelated siblings. Preserve
explicit external media links; broad publishing/sharing is separate work.

* Accepted edits and answers
Reuse Omega's buffer owner and revision-checked publication for both source
editing and structured feedback. Preserve existing =:answer=, =:note=, =:at=
and =:by= source attributes, unrelated bytes and ordinary editor compatibility.
The current kit's read/patch/rename writer does not supply a concurrency guard;
atomic replacement alone cannot coordinate it with an editor or another answer.

An answer carries document ID, block ID, base/question revision and a retry ID.
The owner validates the current question and serializes the accepted mutation.
Refuse a changed/deleted question with the person's answer retained for review.
Concurrent answer submissions resolve once; duplicate delivery does not create
another answer or task continuation. Use existing buffer conflict behavior for
source edits rather than silently replacing another writer's changes.

Project unanswered =ask=/=decision= blocks into the existing Needs you inbox,
with source block, place and linked task. Other feedback remains available in
the document and can contribute counts without pretending every review item
is an agent waiting for an answer. Do not manufacture a task for every block.

An accepted answer records a recoverable delivery to the linked task through
its existing message/continuation authority. Track saved and delivered states
separately, retry idempotently after restart, and reconcile interrupted delivery.
Do not claim a filesystem write and a fact transaction are automatically atomic.
Unlinked decisions remain valid document answers. Reading a file or refreshing
an inbox never repeats a tool effect or resumes work on its own.
